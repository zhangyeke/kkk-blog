## 代码优化

### 文章列表查询

`getAllPosts` 从宽泛的 `include` 改为显式 `postListSelect`：只查询列表与摘要所需的字段、分类名称和作者名称/头像。文章正文仍在服务端用于生成摘要，但不会随列表结果发送到客户端；不再额外查询作者邮箱、作者 ID、分类其他字段及模型的其他字段。类型和服务测试同步更新。

### 照片地图首屏

照片地图改用 `next/dynamic` 延迟加载 `PhotoWallDesktop` 与 `GalleryModal`。地点侧栏在首次打开前不挂载；用户首次打开后保留组件，之后重复打开可复用已加载内容。地图页面的 route entry JavaScript 因此变小。

## 性能测量

### 照片地图 route entry

分别以基线提交和优化提交运行隔离的 `next build --webpack`，通过 `NEXT_DIST_DIR` 写入独立输出目录。数据只统计 `/blog/pictures/map` 的 route entry JS 文件，gzip 使用 Node `zlib` 默认设置。

| 指标 | 基线 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| Route entry JS | 18,841 B | 16,038 B | -2,803 B（-14.88%） |
| Route entry gzip | 7,013 B | 5,751 B | -1,262 B（-18.00%） |

这组构建产物数据可复现地说明地图路由入口脚本减少。它不包含共享运行时、CSS、服务端产物和异步分块，也不能直接等同于完整页面下载量或用户加载时间。

### 文章列表受控样本

离线脚本调用基线和优化后的真实服务函数，使用 6 篇合成文章、每篇 18,000 B 正文、模拟每次数据库调用 30 ms，先预热 1 次，再各测 7 次；不连接数据库，不访问生产服务。

| 指标 | 基线 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| JSON 响应体 | 3,332 B | 2,600 B | -732 B（-21.97%） |
| gzip JSON | 490 B | 444 B | -46 B（-9.39%） |
| 7 次运行中位耗时 | 305.74 ms | 280.35 ms | 样本波动较大，不作为提速结论 |

前后耗时样本范围明显重叠，因此不声称服务端响应更快。此测试衡量的是固定合成数据下的序列化大小和本地受控耗时，不代表真实用户网络或数据库表现。

原始数据见 [`build-2026-11-16.json`](performance/build-2026-11-16.json) 与 [`benchmark-2026-11-16.json`](performance/benchmark-2026-11-16.json)。
